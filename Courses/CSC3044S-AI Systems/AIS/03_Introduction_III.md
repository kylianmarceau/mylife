## Core Content

### Recall Types Of Rational Agents

#### Definitions

> **Reactive (Reflexive) Agent**: An agent that maps current percepts directly to actions, with at most a very simple internal representation of the world.

> **Deliberative (Goal-Based) Agent**: An agent that reasons about goals, typically by building a world model and generating a plan before acting.

> **Learning Agent**: An agent whose behaviour improves from experience, e.g. via reinforcement learning (RL), artificial neural networks (ANN), or large language models (LLM).

The three agent types from earlier lectures are:

| Agent Type | Core Idea |
|---|---|
| Reactive (reflexive) | Stimulus $\rightarrow$ response, little or no internal state |
| Deliberative (goal-based) | Sense $\rightarrow$ plan $\rightarrow$ act, using a world model |
| Learning (RL, ANN, LLM, ...) | A sub-type of deliberative agent whose decision-making is learned |

Learning agents are listed as a sub-category under deliberative (goal-based) agents. This lecture focuses on deliberative agents, including modern LLM-based ones.

### AI Assistants, Generative AI, And AI Agents

#### Definitions

> **AI Assistant**: A system (e.g. Microsoft 365 Copilot, IBM watsonx, Siri, Alexa-style smart speakers, ChatGPT, Claude, Gemini, Perplexity, Grok, DeepSeek used as chat tools) that responds to user requests with fairly limited, user-driven functionality.

> **Generative AI**: AI that generates new content (text, code, speech, or even another program/assistant) from a prompt.

> **AI Agent**: A system that autonomously maps (often multi-modal) sensory inputs to actions in an environment to achieve goals.

The distinction is about autonomy and scope of action, not about which model is underneath.

**Example 1: Personal booking assistant (generated by generative AI).**

- A generative model (GPT-5.2) is prompted to *produce* an assistant.
- The system prompt sets out:
  - **Role & Goal**: "You are Mark, a friendly and professional personal assistant." Its sole objective is to place an outbound phone call to a restaurant and book a reservation for a client (Osamah).
  - **Persona & Tone**: friendly and natural (warm, polite, conversational); concise (brief, like natural dialogue); pacing (must insert pauses using an ellipsis "..." between sentences, e.g. "I'd like to make a reservation for two people... would 7 PM be possible?").
  - **Core Instructions & Conversation Flow**: starting with an initial response, then the rest of the call script.
- **Output**: an automated assistant that phones restaurants to make bookings.

The generated assistant calls various restaurants in a city, looking for a reservation for $N$ people with specific seating and dietary requirements. The user's prompt to the assistant contains:

1. Reservation time.
2. Number of people.
3. Dietary requirements (preferences).

So generative AI *produced* the assistant, and the assistant carries out a narrow, scripted task for the user.

**Example 2: Autonomous ride-hailing vehicle.** The vehicle picks up and drops off customers in a city, based on the highest-value ride requests from a mobile app.

| Component | Classification | Why |
|---|---|---|
| Autonomous vehicle | AI agent (complex) | Maps multi-modal sensory inputs (traffic, obstacles, weather, lighting conditions, ...) to motor outputs (a safe trip from pick-up to drop-off) |
| Ride-request mobile app | Closer to an AI assistant (could itself have been AI-generated) | Very limited functionality: takes requests and passes them on |

### What Is An Agent Model Plus Harness

#### Definitions

> **Agent (modern usage)**: A model placed inside a loop so that it *acts*, not just responds.

> **Model**: The learned component that generates outputs, e.g. an LLM.

> **Agent Harness**: Everything around the model. It wraps the model to manage long-running tasks reliably: the model generates responses, the harness handles everything else.

> **Chain**: A fixed, pre-scripted sequence of model calls in which the developer, not the model, decides the steps.

Turning a model into an agent takes two components:

$$
\text{Agent} = \text{Model} + \text{Harness}
$$

Common model families that can sit at the centre of an agent:

| Abbreviation | Model Type |
|---|---|
| LLM | Large Language Model |
| LCM | Latent Consistency Model |
| LAM | Large Action Model |
| MoE | Mixture of Experts |
| VLM | Vision-Language Model |
| SLM | Small Language Model |
| MLM | Masked Language Model |
| SAM | Segment Anything Model |

**Engine and car analogy:**

| Part | Analogy | Role |
|---|---|---|
| Model | The engine | Generates raw power and responses. Probabilistic and powerful, but lacks control. |
| Harness | The car | Provides steering, brakes, and structure. Manages approvals, filesystem access, sub-agents, and errors to reach a destination reliably. |

In short: the model reasons, and the harness governs everything else.

![Agent equals model plus harness](../../../diagrams/CSC3044S-AI%20Systems/AIS/03_Introduction_III/model_harness_pipeline.svg)
*The LLM reasons in the middle; harness modules curate its inputs, gate its outputs, route actions to execute, review or escalate, and observability spans every stage.*

**Model + harness pipeline.** The harness surrounds the LLM with these stages:

1. **Input**: data, queries, and events arrive from outside.
2. **Context assembly**: curates what the model sees (documents, databases, live feeds).
3. **Tool access**: manages credentials and connections (keys, APIs) that the model can use.
4. **LLM**: receives the assembled context and tool access, and reasons.
5. **Output validation**: guardrails check the model's output before any action.
6. **Action routing**: uses confidence, rules, and escalation to send each action to one of three outcomes: **Execute**, **Review** (by a human), or **Escalate**.

Underneath all stages sits **Observability**: every stage is inspectable and auditable.

**What is and is not an agent:**

| System | Agent? | Reason |
|---|---|---|
| Chatbot with browsing | Not in the full sense | Makes one tool call and answers |
| Chain (pre-scripted model calls) | No | The developer hard-codes the steps; the model does not decide what to do next |
| Agent | Yes | The model chooses its own next action inside the loop |

The key difference is that **the model, not the developer, decides execution at each loop iteration**. This is what changed between 2023 and 2026, and it is the source of both the new capabilities and the new failure modes.

### Harness Components

#### Definitions

> **Tools**: Functions the model can call, e.g. run code, internet search, read files, query databases, send emails.

> **Loop**: The cycle in which the harness runs the model, executes any requested tool call, appends the result to the context, and runs the model again until the task is done.

> **Memory**: The mechanism that carries state across many loop iterations.

> **Permissions**: What the agent is allowed to do without asking, e.g. read-only access, writing files, internet access.

The model never executes tools itself. It *requests* a tool call, and the harness executes it and feeds the result back.

![The harness loop](../../../diagrams/CSC3044S-AI%20Systems/AIS/03_Introduction_III/harness_loop.svg)
*The model only requests tool calls; the harness executes them, appends results and re-runs the model until the task is done, with memory and permissions spanning the loop.*

The agent loop, step by step:

1. The harness runs the model on the current context.
2. If the model requests a tool call, the harness executes the tool.
3. The harness appends the tool result to the context.
4. The harness runs the model again.
5. Steps 2-4 repeat until the task is done.

| Component | What It Does | Note |
|---|---|---|
| Tools | Actions the model can request | Executed by the harness, not the model |
| Loop | Repeated model $\rightarrow$ tool $\rightarrow$ context cycle | Makes the model *act* rather than respond once |
| Memory | Keeps state across iterations | Needed for long-running tasks |
| Permissions | Limits what the agent may do unasked | An important safety dial, often on the wrong setting |

### The Harness Is Now The Product

#### Definitions

> **Harness Engineering**: Designing and optimising the harness (prompts, tool definitions, context management, evaluation loop, model-specific tuning) around a model. It is now a research topic in its own right.

How the source of agent performance has shifted:

| Year | What Determines Agent Performance |
|---|---|
| 2023 | Mostly the model: better models $\approx$ better agents |
| 2026 | A *joint* property of model and harness. The harness (prompts, tool definitions, context management, evaluation loop, model-specific tuning) is what companies actually build and sell |

Research examples in harness engineering:

- *Meta-Harness: End-to-End Optimization of Model Harnesses* (Lee et al. 2026).
- *DarwinX: Evolving Agent Harnesses Through Natural Selection* (Zhang et al. 2026).

Harness-building tooling is now a product category. For example, LangChain offers harness-building tools: optimised databases, sandboxes, context management, and personal data protection.

Consequences of the focus shift:

- The question has moved from "which model?" to "which harness?".
- Choosing an agent means choosing a harness as much as a model.

### What Harnesses Mean For Benchmarks

#### Definitions

> **Scaffolding**: The harness configuration (prompts, tools, loop, context handling) wrapped around a model when it is evaluated.

> **SOTA (State Of The Art)**: The best reported result on a benchmark at a given time.

If the harness alone can change a benchmark score by about 10%, a leaderboard entry for model $Y$ means little without knowing the scaffolding configuration.

- **Terminal-Bench 4.0** shows this: running $N$ different harnesses on the same model $Y$ gives $N$ different scores.
- Given the claim "Model $Y$ yields SOTA on benchmark $X$", the right follow-up question is: *which harness?*
- A strong model that is badly scaffolded will underperform a weaker model in a better harness. Benchmark numbers need context to mean anything.

Terminal-Bench 4.0 ("a benchmark to measure and evolve with the frontier of agent work") lists both the **model** and the **agent harness** for each entry, ranked by resolution rate.

![Terminal-Bench 4.0 by harness](../../../diagrams/CSC3044S-AI%20Systems/AIS/03_Introduction_III/terminal_bench_harnesses.svg)
*Top ten Terminal-Bench 4.0 entries coloured by harness (Codex, Claude Code, Grok Build, mini-SWE-agent); the same model family scores very differently depending on version and scaffolding.*

Each score is really a (model, harness) pair, not a model alone.

### Agent Evaluation With Benchmarks

#### Definitions

> **Benchmark**: A standardised set of tasks used to evaluate and compare models or agents. It acts as a proxy for some problem-solving capability.

> **Saturated Benchmark**: A benchmark on which SOTA exceeds roughly 90%, so it no longer discriminates between models; the remaining gap is largely noise.

The main way agents are evaluated is with benchmarks. A snapshot of major benchmarks (SOTA as of September 2026):

| Benchmark | What It Measures | SOTA (Sept 2026) | Created By / Notes |
|---|---|---|---|
| FrontierMath | 338 research-level maths problems (295 Tier 1-3 + 43 Tier 4); re-released as v2 in June 2026 after an error audit | GPT-5.6 Sol, 89.0% | Epoch AI; problems set by IMO gold medallists and Fields Medal recipients |
| GPQA Diamond | Graduate-level physics, biology, and chemistry reasoning; designed to be "Google-proof" | Gemini 3.8 Flash, 95.3% | Now past the 65-70% human-expert band; effectively saturated |
| SWE-bench Verified | Real-world software engineering: GitHub issues with verified, human-validated solutions | Claude Fable 5, 95.0% | Princeton/Anthropic-validated subset; saturated, SWE-bench Pro is the successor |
| AIME 2026 | American Invitational Mathematics Examination, high-school olympiad level | GLM-5.2, 99.2% | Saturated; no longer discriminating at the top |
| MCP-Atlas | Multi-tool agentic workflows: 1,000 tasks over 36 real MCP servers and 220 tools | Muse Spark 1.1, 88.1% | Scale AI (Scale Labs); LLM-as-judge in a Docker sandbox |
| HLE (Humanity's Last Exam) | 2,500 expert-written questions across 100+ subjects at the frontier of human knowledge | Claude Fable 5.1, 65.0% | Center for AI Safety + Scale AI; published in *Nature*, Jan 2026 |
| Codeforces (Elo) | Competitive programming rating against human contestants | DeepSeek V4 Pro, 3206 | Unchanged since May; an open-weights model still leads |

![Benchmark saturation](../../../diagrams/CSC3044S-AI%20Systems/AIS/03_Introduction_III/benchmark_saturation.svg)
*SOTA per benchmark (Codeforces is an Elo rating, so it is omitted); AIME, GPQA Diamond and SWE-bench Verified sit past the ~90% line and no longer discriminate.*

Three general problems when reading benchmark results:

| Problem | Meaning | Implication |
|---|---|---|
| **Mismatch** | 90% on benchmark $X$ does not mean 90% on benchmark $Y$ | Benchmarks measure different things at different difficulty levels |
| **Saturation** | Once SOTA $> \sim 90\%$, the benchmark stops discriminating | Remaining differences are largely noise |
| **Selection** | Developers pick benchmarks favourable to their model | Check performance on benchmarks where *other* models lead |

### Goodhart's Postulates

#### Definitions

> **Goodhart's Postulate I**: Benchmarks are not real-world use.

> **Goodhart's Postulate II (Goodhart's Law)**: "When a measure becomes a target, it ceases to be a good measure."

> **Proxy**: A measurable quantity used to stand in for an underlying capability that is hard to measure directly.

Benchmarks are proxies for some problem-solving capability. For example, a high FrontierMath score is taken as evidence that a model can do research-level mathematics.

The problem arises when benchmarks become the "ultimate goal" for model quality:

1. Labs train and tune models *specifically* to perform well on benchmarks.
2. The benchmark stops being a proxy for capability and becomes a model optimisation objective.
3. It is then no longer a good measure of the underlying capability it was meant to track.

| Postulate | Statement | Consequence For AI Evaluation |
|---|---|---|
| I | Benchmarks are not real-world use | A benchmark tests a narrow, well-defined slice of a skill, not the full real-world task |
| II | When a measure becomes a target, it ceases to be a good measure | Optimising for the benchmark inflates scores without matching gains in capability |

### Example SWE-Bench Versus Program-Bench

> **SWE-bench**: A benchmark that tests agents on solving real-world software engineering problems from live GitHub repositories. It provides a codebase, an issue description, and an execution environment, and scores models on whether their generated patches pass the repository's unit tests.

> **SWE-bench Verified**: A human-filtered subset of 500 SWE-bench instances.

> **Program-Bench**: A benchmark that tests whether a model can design and build real-world, functional software (200 tasks).

### Benchmark Contamination And Training Data Leakage

#### Definitions

> **Benchmark Contamination (Training Data Leakage)**: When benchmark questions and answers appear in a model's training data, so the model may have already seen the solutions.

> **Held-Out Benchmark**: A benchmark built from new, unpublished problems, with some problems deliberately kept secret.

> **Refreshed Benchmark**: An existing benchmark revised to be harder and less memorisable.

> **Dynamic Benchmark**: A benchmark that keeps generating new test items as the dataset expands.

A benchmark measures model capability *only if* the model has not already seen the solutions. Contamination happens like this:

1. Most benchmarks are published online.
2. Models are trained on online data.
3. So models have usually seen the benchmark questions and answers during training.
4. The resulting inflated scores do not reflect general problem solving.

**Implication**: scores on popular benchmarks (all of which appear in training data) may overstate a model's general reasoning ability. Commonly affected benchmarks:

| Benchmark | What It Covers |
|---|---|
| MMLU (Massive Multitask Language Understanding) | Broad multi-subject knowledge |
| AIME | Standardised mathematics exam |
| GSM8K | 8,500 human-written mathematics problems |
| HumanEval | Evaluates generated Python code |

**Mitigations:**

| Mitigation | Example | How It Helps |
|---|---|---|
| Held-out benchmarks | FrontierMath: built as 350 new (unpublished) problems, with 20 explicitly held out | Problems cannot be in training data |
| Refreshed benchmarks | MMLU-Pro (Wang et al. 2024): harder questions and more answer choices | Memorisation helps less |
| Dynamic benchmarks | LatestEval (reading comprehension): new items generated as the dataset expands | Test items post-date training data |

Overall implication: model evaluations should use data held out from training. Otherwise there is no way to know whether the benchmark was in the training data.

### What Benchmarks Do Not Test And Why They Fail

#### Definitions

> **Edge / Outlier Case**: An unusual input that differs from the typical cases a model was optimised or tested on.

> **African (Low-Resource) Gap**: The mismatch between mainstream benchmarks and low-resource contexts (such as African languages and settings), so benchmark results answer questions out of context.

Benchmarks test only a narrow problem set, which is usually not indicative of real-world problem solving.

- Example: a model optimised to solve vehicle routing problem test cases may not perform well on real-world vehicle routing problems.
- The issue is unseen, unusual "edge" or "outlier" cases that the evaluation set does not contain.

The three failures of AI system benchmarks:

| Failure | Effect |
|---|---|
| Goodhart's postulate | Benchmarks measure benchmark performance, not real-world capability |
| Contamination | Even that benchmark performance is often inflated by overlap between training and test data |
| African (low-resource) gap | Benchmarks answer questions out of context for low-resource settings |

### Agent Architectures

#### Definitions

> **Agent Architecture (Maes, 1991)**: "A particular methodology for building agents. It specifies how the agent can be decomposed into the construction of a set of component modules and how these modules should be made to interact. The total set of modules and their interactions has to provide an answer to the question of how the sensor data and the current internal state of the agent determine the actions and future internal state of the agent. An architecture encompasses techniques and algorithms that support this methodology."

> **Agent Architecture (Kaelbling, 1991)**: "A specific collection of software (or hardware) modules, typically designated by boxes with arrows indicating the data and control flow among the modules. A more abstract view of an architecture is as a general methodology for designing particular modular decompositions for particular tasks."

> **Hybrid Architecture**: An architecture that combines components of different kinds, e.g. a learned model (reasoning) inside a structured, rule-governed harness (control).

Both definitions share the same core: an architecture is a **modular decomposition** of an agent plus the **interactions (data and control flow)** between modules, which together determine how inputs and internal state produce actions and the next internal state.

The modern "Agent = Model + Harness" design is an example of a **hybrid architecture**: the LLM reasons, while the harness modules (context assembly, tool access, output validation, action routing, observability) govern everything else. See [[#What Is An Agent Model Plus Harness|What Is An Agent Model Plus Harness]] for the full pipeline.

**Families of agent architectures**: reactive agents, deliberative agents, hybrid agents, multi-agent systems, and neuro-agents.

![Agent architecture families](../../../diagrams/CSC3044S-AI%20Systems/AIS/03_Introduction_III/architecture_families.svg)
*All five families sit inside the rational boundary, but hybrid agents and neuro-agents are also flagged "Irrational?".*

**Where are the rational agents?** All five families can be designed as rational agents. Hybrid agents and neuro-agents are flagged as possibly **irrational**: they rely on learned (neural) components whose decisions are not derived from explicit reasoning, so their rationality is open to question.

### Reactive Agent Architectures

#### Definitions

> **Reactive Agent Architecture**: An architecture in which the agent has at most a very simple internal representation of the world but tightly couples perception and action.

> **Behaviour-Based Paradigm**: The view that agent behaviour is built from a set of simple stimulus-response behaviours rather than from symbolic reasoning.

> **Subsumption Architecture**: Brooks' (1991) layered reactive architecture, from "Intelligence Without Representation".

> **Emergent Behaviour**: Complex group-level behaviour that arises from simple local interactions between agents, without central control.

![Reactive agent architecture](../../../diagrams/CSC3044S-AI%20Systems/AIS/03_Introduction_III/reactive_agent.svg)
*Sensors feed a bank of stimulus-response behaviours, each mapping a sensed state directly to an action sent to the effectors; there is no world model or planner.*

Key properties:

- At most a very simple internal world representation.
- Tight coupling of perception and action.
- Follows the behaviour-based paradigm.
- Intelligence is a product of the **interaction between an agent and its environment**, not of internal reasoning.

**Examples of reactive architectures:**

| Example | Type | Reference |
|---|---|---|
| Subsumption architecture | Single-agent reactive architecture | Brooks (1991), *Intelligence Without Representation*, Artificial Intelligence 47: 139-159 |
| Boids | Emergent-behaviour multi-agent model (flocks, herds, schools) | Reynolds (1987), *Flocks, herds and schools: A distributed behavioral model*, SIGGRAPH |
| Stigmergy model | Emergent-behaviour multi-agent model (coordination in distributed building) | Theraulaz & Bonabeau (1995), *Science* 269: 686-688 |

A few other emergent-behaviour multi-agent models also fit here.

### Deliberative Agent Architectures

#### Definitions

> **Deliberative Agent Architecture**: A framework for **sense-plan-act**: how agents sense their environment, generate a plan, and act on the plan.

> **World Model**: The agent's internal representation of the state of the environment.

> **Planner**: The module that generates a plan (sequence of actions) from the world model and goals.

> **Plan Executor**: The module that carries out the plan through the effectors.

![Deliberative agent architecture](../../../diagrams/CSC3044S-AI%20Systems/AIS/03_Introduction_III/deliberative_agent.svg)
*Sense-plan-act: sensors update the world model, the planner builds a plan, and the plan executor drives the effectors.*

Deliberative agent behaviour is dictated by:

- the **environment state**,
- the **internal state**, and
- the **plan**, which may come from logical reasoning, symbolic manipulation, a rule set, an ANN, and so on.

Together these map inputs $\rightarrow$ outputs.

| | Reactive | Deliberative |
|---|---|---|
| Internal representation | At most very simple | Explicit world model |
| Pipeline | Sensors $\rightarrow$ stimulus-response rules $\rightarrow$ effectors | Sensors $\rightarrow$ world model $\rightarrow$ planner $\rightarrow$ plan executor $\rightarrow$ effectors |
| Source of intelligence | Agent-environment interaction | Reasoning/planning over the world model |
| Paradigm | Behaviour-based | Sense-plan-act |

**Examples of deliberative architectures:**

| Example | Reference |
|---|---|
| Belief, Desire, Intention (BDI) architecture | Rao & Georgeff (1991), *Modeling Rational Agents within a BDI-Architecture*, KR'91, pp. 473-484 |
| Agent-Oriented Programming | Shoham (1990), Technical Report, Stanford University |
| Deductive reasoning agents | Walton (2006), *Practical reasoning and deductive agents*, Agency and the Semantic Web |

### Deductive Reasoning Agents

#### Definitions

> **Deductive Reasoning Agent**: A deliberative agent that decides what to do by **theorem proving**: it uses logic to encode a theory stating the best action to perform in any given situation.

> **$\rho$ (rule theory)**: The theory, i.e. the set of deduction rules, that encodes which action is best in each situation.

> **$\Delta$ (database)**: A logical database describing the current state of the world.

> **$Ac$ (action set)**: The set of actions the agent can perform.

> **$\Delta \vdash_\rho \phi$**: The formula $\phi$ can be proved from the database $\Delta$ using the rules $\rho$.

> **$Do(\alpha)$**: A predicate meaning "action $\alpha$ should be performed".

The agent selects an action in two passes, then gives up:

```text
for each α ∈ Ac do                 /* try to find an action explicitly prescribed */
    if Δ ⊢ρ Do(α) then
        return α
    end-if
end-for

for each α ∈ Ac do                 /* try to find an action not excluded */
    if Δ ⊬ρ ¬Do(α) then
        return α
    end-if
end-for

return null                        /* no action found */
```

Step by step:

1. **Prescribed action**: for each $\alpha \in Ac$, check whether $\Delta \vdash_\rho Do(\alpha)$. If the rules prove that $\alpha$ should be done, return $\alpha$.
2. **Non-excluded action**: if no action is prescribed, for each $\alpha \in Ac$ check whether $\Delta \nvdash_\rho \neg Do(\alpha)$. If the rules cannot prove that $\alpha$ is forbidden, return $\alpha$ as an acceptable fallback.
3. **No action**: if every action is excluded, return null.

Formally, the first pass looks for $\alpha$ such that $\Delta \vdash_\rho Do(\alpha)$, and the second for $\alpha$ such that $\Delta \nvdash_\rho \neg Do(\alpha)$.

### The Vacuum World

#### Definitions

> **Vacuum World**: A $3 \times 3$ grid world (coordinates $x, y \in \{0, 1, 2\}$) in which a robot vacuum must clear up all dirt.

> **$In(x, y)$**: The agent is at $(x, y)$.

> **$Dirt(x, y)$**: There is dirt at $(x, y)$.

> **$Facing(d)$**: The agent is facing direction $d$.

**Setup:**

- The robot starts at $(0, 0)$.
- Dirt is at $(0, 2)$ and $(1, 2)$ (the top-left two cells).
- Goal: clear up all dirt.
- Actions: $Ac = \{turn, forward, suck\}$, where *turn* means turn right.

*The 3x3 vacuum world: robot at (0,0) facing north, dirt at (0,2) and (1,2); the dashed route is what the rules below produce.*

Initial database:

$$
\Delta_0 = \{ In(0,0),\ Facing(north),\ Dirt(0,2),\ Dirt(1,2) \}
$$

**Example run.** Each state lists the robot's position, heading, and remaining dirt:

![Vacuum world example run](../../../diagrams/CSC3044S-AI%20Systems/AIS/03_Introduction_III/vacuum_example_run.svg)
*State-transition graph from the start state; the top branch removes Dirt(0,2), while the bottom branch heads east and sucking a clean cell (self-loop) changes nothing.*

The top branch (forward, forward, suck) reaches and cleans the first dirt cell. The bottom branch shows that wrong choices (turning east, sucking a clean cell) waste actions without progress.

**Rules $\rho$ for deciding what to do:**

$$
\begin{aligned}
In(0,0) \land Facing(north) \land \neg Dirt(0,0) &\longrightarrow Do(forward) \\
In(0,1) \land Facing(north) \land \neg Dirt(0,1) &\longrightarrow Do(forward) \\
In(0,2) \land Facing(north) \land \neg Dirt(0,2) &\longrightarrow Do(turn) \\
In(0,2) \land Facing(east) &\longrightarrow Do(forward)
\end{aligned}
$$

- The rules drive the robot north up column 0, turn it east at the top, and move it along the top row.
- An extra rule: IF the robot is at $In(0,2)$, THEN reset its position to $(0, 0)$.
- Starting at $(0, 0)$, the robot will clean up the dirt.

These rules depend on a cleaning rule of the form $In(x,y) \land Dirt(x,y) \longrightarrow Do(suck)$ (the robot sucks whenever it is on a dirty cell). This is why the movement rules all require $\neg Dirt$ on the current cell.

### Problems With Deductive Agents And The Roomba Approach

#### Definitions

> **Undecidable**: No algorithm can always determine, in finite time, whether a given statement is provable.

> **NP-Complete**: A problem class solvable in Nondeterministic Polynomial time, with no known efficient (polynomial-time) solution.

> **Roomba**: A commercial robot vacuum that uses reactive, sensor-driven behaviours instead of logical deduction.

The hand-written rule approach works on this tiny grid, but it has serious problems:

| Problem | Explanation |
|---|---|
| Perception / grounding | How do you convert raw video camera input into a symbol such as $Dirt(0, 1)$? |
| Static environment assumption | Decision making assumes the world does not change while the agent reasons |
| Undecidability | Decision making using first-order logic is undecidable |
| Intractability | Even with propositional logic, worst-case decision making is NP-complete: no known efficient solution |

**A better approach: the Roomba.** Real robot vacuums take a reactive, behaviour-based approach instead of theorem proving.

- **Sensors**: infrared sensor, cliff sensor (to avoid falling down stairs), and a smart bumper that detects collisions. A side brush sweeps dirt from edges.
- **Behaviour**: rather than planning a path over a symbolic map, it combines simple movement patterns: spiralling outward from the start point, following walls and furniture edges (e.g. around a sofa and table), and bouncing off obstacles in new directions.
- **Result**: a long-exposure photo of a Roomba's path shows dense, overlapping, criss-crossing lines that cover the whole floor area without any explicit world model.
